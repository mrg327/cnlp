# cnlp: check ESP32 firmware against its plan

`cnlp` is installed on PATH. It **only reads** the project: it copies sources to a
temp dir and analyzes the copy. It never edits code. Run it from the project
root and pass `.` as the project.

## When to run what

| Situation | Command |
| --- | --- |
| Start of a session, or "where am I?" | `cnlp status .` |
| After any change to C code or pins | `cnlp audit .` |
| Questions about verification / requirements | `cnlp evidence .` |
| Before proposing any pin/GPIO change | `cnlp try 'gpio 35 is input "enc sw" with internal pull-up.'` (what-if against the whole pin plan; changes nothing) |
| Questions about cnlp itself, a rule ID, a pin, or what command to use | `cnlp ask "<question>"` (answers from cnlp's own sources; `?` means it doesn't know) |
| Exact flags of a command | `cnlp <cmd> --help` |

Add `--json` when you need to parse the output; the default text is for people.
Exit code 1 means findings with errors, 2 means a usage or setup error.

## How to report results

1. Quote the verdict line (`✓ Audit OK — 2 warnings`, `✗ 1 error`).
2. For each error, give the rule ID, the file:line, and what it means in one plain
   sentence. Rule IDs: `C*`/`W*` chip and module pin rules, `AUDIT_*` plan vs code,
   `RT1`–`RT6` the project's real-time rules, `LINT_*` includes and APIs.
3. Warnings and "planned pins not configured yet" are informational mid-project.
   Say which phase introduces them when `cnlp status` shows it.
4. Suggest a fix as its own small change **for the user to review**. Do not apply
   fixes just because cnlp reported something. The project's own rules (its
   CLAUDE.md / AGENTS.md) come first: if it says the user writes and reviews
   each change, explain the problem and let them decide.

## Never

- Never run `cnlp flash`, `cnlp gate answer`, `cnlp gate review`, `cnlp evidence add`
  or `cnlp measure --record`. Those record approvals or measurements in the user's
  name. Show the exact command and let the user run it.
- Never claim a requirement passed or a measurement was taken unless
  `cnlp evidence .` shows it.
- Never edit files under `components/board/` or anything marked "GENERATED by cnlp".
- Never touch the scope or flash the board from cnlp unless the user asks.

## Recording a measurement (user runs it)

```bash
cnlp measure period --ch 1 --samples 20 --criterion "1 ms ±2%" --record . R4 --source-note "GPIO 2 scan probe"
cnlp evidence add . R4 measured_scope pass --value 1.000 --unit ms --criterion "1 ms ±2%"
```

## If a command says there's no config

`cnlp` keeps project configs in its own repo (`~/projects/cnlp/projects/<name>/`),
never in the project. If `cnlp status .` reports "No audit config", tell the user;
don't create one inside their project.
